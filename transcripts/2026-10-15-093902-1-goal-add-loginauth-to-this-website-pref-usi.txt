⏺ Yes, this is feasible, and your GitHub Action needs no changes. The repo
  already contains most of an auth system. Google sign-in is an add-on that
  mints the cookie you already have, not a rebuild.

  What you already have

  The site is not a plain static site anymore. There is a hand-rolled auth layer
  in netlify/functions/ with register, login, session, logout, password reset
  and admin-approval functions. Users live in a Netlify Blobs store as one JSON
  document. Logins get a 12-hour HMAC-signed cookie. An edge function in
  netlify/edge-functions/require-auth.js checks that cookie on every request to
  the weeks, core and admin paths.

  Live state on theailab.net right now, checked with curl:

  - The session function and the edge gate are deployed and working.
  - The admin path redirects to login as designed.
  - Course pages are open because the gate's environment variable is set to off.

  The deploy workflow already runs npm install, bundles functions and edge
  functions, and ships them with the Netlify CLI. The public-sync allowlist
  already includes the netlify folder, package.json and the root login pages. So
  the only workflow fact that matters is that the Google secrets go in
  Netlify's site environment, not GitHub secrets, because the functions run on
  Netlify.

  Options, ranked

  1. Server-side Google OAuth in two Netlify Functions. Recommended. One
  function redirects to Google with a state cookie and PKCE. A callback function
  exchanges the code for an ID token, checks issuer, audience, expiry and
  email-verified, finds or creates the user by email, then calls your existing
  makeSessionCookie and redirects to the next path. The edge gate does not
  change at all. No client-side JavaScript beyond a link. Roughly 150 lines,
  zero or one dependency, free at any plausible class size. Google asks for no
  app verification when you request only the openid, email and profile scopes.
  One Google Cloud project, one web OAuth client, and a published external
  consent screen are the whole setup.

  2. The "Sign in with Google" button from Google Identity Services. A Google
  script renders the button and hands your page an ID token. You post it to one
  function that verifies it and mints the same cookie. Faster to build, but it
  depends on a third-party script, ad blockers and the FedCM migration in
  Chrome. Pick this only if you want One Tap.

  3. A hosted identity provider. Auth0 and Clerk both have free tiers far beyond
  a course roster. You would gain a login UI, MFA and passwordless for free,
  but you would add an SDK, a vendor, and a bridge that verifies their token at
  your edge gate. Overkill for one course site.

  4. Netlify Identity. Netlify announced its deprecation in 2025 and reversed
  that in February 2026. It supports Google, but the widget is old and the year
  of uncertainty is a warning sign. Not for a new build.

  5. Netlify's built-in site protection. Paid plan only. No.

  Free-tier headroom, for the recommended path:

  ┌──────────────────────────────────┬───────────────────────────────┐
  │             Resource             │   Free allowance per month    │
  ├──────────────────────────────────┼───────────────────────────────┤
  │ Netlify Functions                │ 125,000 invocations           │
  ├──────────────────────────────────┼───────────────────────────────┤
  │ Netlify Edge Functions           │ 1,000,000 invocations         │

  ├──────────────────────────────────┼───────────────────────────────┤
  │ Clerk, if chosen instead         │ 50,000 monthly retained users │
  └──────────────────────────────────┴───────────────────────────────┘

  Decisions to settle before building

  - Who gets in. A roster allowlist of emails that auto-approves on first Google
    login is the cleanest fit. Keep the existing admin-approval queue for
    anyone not on the roster. Auto-approving every kenyon.edu address is a
    reasonable shortcut.
  - Whether to retire password auth. Dropping it removes five functions, four
    HTML pages, scrypt hashing and the Resend email dependency. Linking existing
    accounts by email makes the switch painless. I would retire it after one
    semester of both.
  - When to turn the gate on. It is one environment variable, and the fail-safe
    default is gated, so set it deliberately.
  - Redirect safety. The next parameter should accept only paths that start with
    a single slash.
  - Tests. The claims-validation logic belongs in a pure module with node tests
    like the existing decide-access tests. The pytest suite will also need the
    new login page to pass its no-stub checks.
